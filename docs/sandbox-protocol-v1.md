# RootAgent Sandbox Protocol v1

Status: contract definition; no operational gRPC client exists in this release.

## Purpose and compatibility

This protocol defines the boundary between RootAgent and a future isolated code
runtime. Version 1 is additive: implementations may add optional response fields but
must not change field meaning, hash rules, lifecycle ordering, or stable status codes.
A breaking change requires a new protocol version and a client/server capability
negotiation step. Selecting `EXECUTOR_BACKEND=grpc` before a compatible client is
implemented makes readiness unhealthy and execution returns `sandbox_unavailable`.

The in-process local executor implements the same application lifecycle for
development and compatibility. It is not a sandbox. Python-level import and path
checks do not prevent pandas, NumPy, native libraries, process-wide resource
exhaustion, host file access through undiscovered library APIs, network access, or
secret exfiltration. A deadline cannot stop an already-running Python worker thread.

## Identity and lifecycle

All run, workspace, and artifact identifiers are UUIDs generated by RootAgent. Names
and identifiers supplied by an end user are never used as host or sandbox paths.

1. `CreateWorkspace(run_id, workspace_id, limits)` creates an empty private workspace
   with `inputs/` and `outputs/`. Repeating the same request is either idempotent with
   identical parameters or returns a conflict.
2. RootAgent streams selected inputs with `UploadFile`. The server verifies the
   declared byte count and SHA-256 before making a file visible through an atomic
   rename.
3. `Execute` runs code with a relative working directory, deadline, output caps, and
   resource settings. It supports client cancellation.
4. `ListOutputs` returns manifests for regular files below `outputs/`.
5. `DownloadFile` streams a selected output; RootAgent verifies size and SHA-256 again.
6. `DestroyWorkspace` is idempotent and removes all data and execution state.

RootAgent calls destroy in a `finally` path. The runtime must also enforce an
independent workspace TTL and reconcile abandoned workspaces.

## Streaming transfers

Upload and download streams begin with metadata followed by bounded byte chunks. The
metadata includes protocol version, workspace UUID, safe relative path, media type,
declared size, and lowercase hexadecimal SHA-256. Servers reject a stream that exceeds
its declared size or quota before committing the file. Partial files remain invisible
and are deleted after cancellation or failure. Download responses include the same
metadata and never return host filesystem paths or object-store credentials.

## Execution

An execution request contains code, workspace UUID, contained working directory,
absolute deadline, stdout/stderr byte caps, and optional CPU, memory, and process
limits. The service streams bounded stdout/stderr records and finishes with one stable
status:

- `succeeded`
- `failed`
- `timed_out`
- `cancelled`
- `sandbox_unavailable`

The terminal response includes exit code when available, duration, truncation flags,
and output manifests. A timeout or cancellation must terminate the isolated process
tree before the workspace can be reused or destroyed. RootAgent may cancel the RPC at
any point; cancellation is not interpreted as permission to continue execution.

## Output manifests and quotas

Each manifest contains safe basename, contained relative path, media type, byte size,
SHA-256, creation source, and optional raster dimensions. The service returns only
regular files. Default RootAgent limits are 20 files, 50 MiB per file, and 100 MiB per
run. The application subsequently validates allowed PNG, CSV, and XLSX contents; a
media type or extension alone never establishes trust.

## Path and filesystem rules

Paths are UTF-8 relative paths with no empty component, `.`/`..`, absolute prefix,
drive prefix, NUL, or platform separator ambiguity. Both client and server resolve and
verify containment. Symlinks, hard links, devices, FIFOs, sockets, mount points, and
archive traversal entries are rejected. Inputs become read-only after staging.
Outputs are created atomically beneath `outputs/`. Safe filenames are internal,
collision-resistant names; display filenames are metadata only.

## Transport security and service authentication

Production communication requires TLS with server-name validation and service
authentication. Mutual TLS is preferred; a short-lived scoped bearer credential may
be used in addition. Certificates and tokens come from mounted secrets or a workload
identity provider, never chat data, model prompts, logs, container images, or protocol
error messages. Servers authorize the RootAgent service identity, apply replay
protection where applicable, rotate credentials, and emit auditable lifecycle events.

Errors sent to clients use stable codes and safe messages. Full internal exceptions
remain in access-controlled server logs correlated by run/workspace identifiers.
